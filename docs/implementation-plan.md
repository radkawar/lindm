# Implementation sequence and decision gates

Status: G0, the internal G1 control plane and G2 native-agent qualification are
reviewed and committed. G3 connected service dispatch and G3A admin authentication
modes are implemented, natively or browser-exercised and independently reviewed
(see the ledger). R1 qualification is still open: remaining R1 platform branches,
live Entra tenant evidence, release/operations gates and measured capacity.

The owner has replaced the all-features-at-launch contract with R1: connected
Ubuntu LTS and Fedora/RHEL service-state and inventory management. The exact
[release allocation](product-specification.md#3-release-requirements-and-allocation)
and [resource/platform coverage](verification.md#resource-kind-coverage) are the
launch boundary. Later capabilities remain a roadmap, not hidden R1 dependencies.
No current evidence establishes a production-ready release.

### First end-to-end implementation slice

G1 and G2 establish one narrow but real path: start the single-host server with real
PostgreSQL and an OIDC IdP; authenticate an admin; issue one-use enrollment authority;
install the built agent package in a disposable VM; establish mTLS; collect actual
inventory; show it in the console; revoke identity and prove subsequent sync denied.
Add the RPM-family execution before calling this slice cross-distro. Do not implement
high-risk provider actions before the identity/audit/durability invariants work.

The next vertical slice is G3, not another isolated native worker: assign one
immutable service revision to one enrolled device from the authenticated console,
deliver work through the production device transport, obtain executor-generated
preparation/challenge evidence, authorize start on the server, ingest a nonce-bound
device attestation and display the actual terminal result. Preserve existing signing,
fresh actor authorization, mTLS/session and journal boundaries. Queue acceptance is
not success. Exercise the uncertain/replayed/revised path before adding providers.

The unverified production install-projection worker draft is deferred outside the
active checkout. The committed copied-input experiments retain their narrow evidence;
they are not a prerequisite for proving this existing service execution path.

No demo-only no-auth mode, token in a shell history, fake SSO provider, in-memory
production store, generic shell executor, or hardcoded inventory is an acceptable
shortcut. Test credentials are legitimate isolated IdP/PKI fixtures, not production
fallbacks. The same migrations, generated clients and domain authorization serve UI,
CLI and worker paths.

## 3. Decision ownership and readiness

Confirmed user decisions: greenfield; Go/protobuf/sqlc; separate agent; single-tenant
single-host-capable backend; desktop-first plus servers; maintained automation, hooks
and production-quality engineering; independent review of each slice.

Release-scope decision (supersedes the earlier all-at-launch clarification): R1 is
connected, non-destructive Ubuntu LTS and Fedora/RHEL service-state and inventory
management with local administrators and optional Keycloak/Entra. Air-gap, person
entitlements, other identity providers, remote assistance, destructive capabilities,
other mutable families, the rolling release (Arch/Tumbleweed) and the Atomic and
NixOS products all remain committed roadmap with their own gates. Their cost is never
hidden behind inventory-only support or a generic mutable-package adapter.

Greenfield persistence: nothing is deployed, so changed decisions rewrite existing
migrations and local schemas in place. Development and lab databases are reset rather
than upgraded. Upgrade/migration paths begin with the first shipped release.

Engineering defaults selected for review: modular monolith; PostgreSQL/pgx/sqlc;
Connect; OIDC client with optional SCIM later; native providers; SQLite agent journal;
separated executor/session processes; TUF updates; QEMU/libvirt/openQA laboratory;
no mandatory broker/cache or Kubernetes. Security findings may change these choices
before implementation. Package/library versions are pinned at G1 after compatibility
and maintenance checks, not invented here.

## 4. Review and acceptance protocol

Independent reviewers cover (1) commercial product scope and ambiguity, (2) protocol,
authorization, endpoint/security and destructive safety, and (3) deployment/air-gap,
scaling, distro/lifecycle testing and developer automation. Reviewers work read-only;
one integration owner edits the specifications to prevent conflicting fixes.

A finding records severity, exact location, failure scenario, proposed correction,
whether it blocks implementation or only its later gate, and who owns the decision.
Resolve factual/design gaps directly. Ask the owner only for materially different
product tradeoffs. Preserve a concise disposition ledger and amend requirements/tests
for accepted findings. Do not treat lack of reviewer feedback as proof of correctness.

The first three independent reviews produced ten accepted findings: two product,
six security/protocol and two operations/testing gaps. Three follow-up reviews
confirmed the main corrections and found one shared residual broker-freshness gap,
also corrected. All eleven corrections and their evidence obligations are tracked
in [review dispositions](review-dispositions.md).

G0 is ready only when the independent review has been reconciled and the first-slice
contract has no unresolved correctness/security ambiguity. Hardware/enterprise access
may remain a clearly named later gate; it is never silently claimed by a release.
